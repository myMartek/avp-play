# visionOS Windows VR research shell

This native SwiftUI visionOS research app provides a launcher window and a `CompositorLayer` immersive scene. It accepts the existing version-1 Windows game manifest, validates it, and calls one persistent `NativePluginWindowsRuntime` from `WindowsVRCore`. The runtime loader accepts a signed `WindowsRuntimePlugin.framework` only from the app's `Frameworks` directory. The embedded plugin adapter invokes Madeira's Wine/FEX bridges. Pinned OpenComposite implements the OpenVR boundary; a project-owned D3D11 OpenXR runtime forwards tracking, controllers and stereo textures through a DXMT/Wine host extension to the native compositor. These are source implementations and build recipes; native archives and guest runtime DLLs have not been built or bundled.

After requesting debugger/JIT preparation, the app opens the immersive scene and waits up to 12 seconds for the compositor to bind its Metal device, publish stereo targets, and supply a fresh tracked head pose. It then dispatches to the embedded runtime plugin. Plugin acceptance means only that a launch request was accepted. Wine process activity is displayed separately from native compositor queue counters; neither establishes game readiness or rendered output.

## Local library and profiles

The app can persist games and named per-game launch profiles in its sandbox Application Support directory (`WindowsVRLibrary/windows-vr-library-v1.json`). The app stores the validated version-1 manifest, profile fields, and a bookmark for the user-selected game folder. It does not acquire or package game files. The Mac CLI transfer command can copy locally owned files directly into this app; use **Mac transfers → Refresh transferred games** to discover completed content generations. See [the transfer guide](../docs/windows-vr-transfer.md). A security-scoped URL returned by the folder picker is accessed while selected; for a saved entry, the bookmark is resolved and access is started only when the user selects that library item, then released when selection changes, a session ends, or the app stops that session. If bookmark access fails, select the folder again and save the game to refresh its bookmark. Library data is local to this app installation and is not synchronized.

Profiles are stored separately from the manifest and from the runtime plugin request. The manifest schema and required V1 plugin fields remain compatible; the optional gameID field selects a per-game Wine prefix. A profile can be selected, saved, saved as a new profile, and removed; its launch arguments are edited as a JSON array of strings, preserving empty and newline-containing argv entries. Profiles also save the ordinary-Metal spatial render scale (50–100%, default 100%); this is bilinear per-eye scaling, not temporal SR or DLSS. Backend and graphics are retained from the manifest/profile rather than exposed as unimplemented graphics controls. D3D12 manifests and transfers are retained as an experimental DXMT request, with launch gated on the matching package advertised by the signed plugin. Vulkan is explicitly blocked without fallback. See [the D3D12 integration contract](../docs/windows-vr-d3d12.md).

The native plugin consumes one session per app process. Imports, library selection, and profile changes are disabled during launch/session activity and after the session slot is consumed. A stop request can return pending while cooperative OpenXR exit is processed. The UI stays active and retains folder permission until Wine actually exits. Unresponsive guests still require app restart; no force-termination or in-process relaunch is claimed.

## Compatibility report and counters

The UI can export a versioned JSON compatibility report containing the device model, OS version/build description, requested game/profile, backend and graphics request, capability status/reasons, Wine status, and the compositor ABI's submitted/acquired/dropped/completed/queued counters when available. Environment variable names are included but values are omitted. Metrics without instrumentation are explicitly `unknown / not measured`, including simulation rate, newly rendered stereo-frame rate, compositor presentation rate, frame times, missed deadlines, latency, memory, sustained thermals, and native-equivalence comparisons. Queue counters are advisory diagnostics, not performance measurements or proof of rendering.

Capabilities are conservative. The version-1 plugin must reject unsupported backend requests and does not select a fallback. The adapter supports a Direct3D 11 path; Vulkan is unsupported. A loadable signed plugin is only conditional availability, not evidence that game startup or frames work. The visionOS 27 SDK marks MetalFX temporal scaling unavailable on the initial target. Frame generation and guest-pipeline foveation are unavailable. The UI exposes no nonfunctional graphics toggles.

## Compositor and controller bridge

The immersive renderer uses CompositorServices `LayerRenderer` timing, drawable eye views, Metal textures, and predicted ARKit device/accessory poses. `windows-vr-native/include/WindowsVRCompositorBridge.h` defines the C ABI consumed through the project-owned DXMT/OpenXR adapter. It exports:

- `wvr_compositor_bind_metal_device_v1`, `wvr_compositor_publish_targets_v1`, `wvr_compositor_copy_targets_v1`, and `wvr_compositor_copy_readiness_v1` for renderer/device setup.
- `wvr_compositor_submit_stereo_frame_v1`, `wvr_compositor_acquire_latest_stereo_frame_v1`, `wvr_compositor_release_acquired_frame_v1`, `wvr_compositor_copy_consumer_event_v1`, and `wvr_compositor_copy_stats_v1` for bounded stereo GPU-texture handoff. The queue holds three frames, drops stale queued frames, and retires consumer-event values in ticket order.
- `wvr_compositor_publish_frame_tracking_v1` and `wvr_compositor_copy_frame_tracking_v1` for predicted head pose, per-eye transforms/projections, frustum angles, and timestamp.
- `wvr_compositor_publish_controller_state_v1`, `wvr_compositor_copy_controller_state_v1`, `wvr_compositor_submit_haptic_v1`, and `wvr_compositor_take_haptic_v1` for tracked spatial-controller pose/actions and bounded haptic requests.

The controller provider adapts GameController spatial accessories through ARKit `AccessoryTrackingProvider`, samples normalized button/trigger/grip/stick inputs, and best-effort routes haptics through CoreHaptics. Its API shape was cross-checked against the checked-in ALVR visionOS source; ALVR is not a build or runtime dependency. Incoming eye textures must be single-sample 2D Metal textures on the compositor's exact `MTLDevice`, with the published target dimensions and pixel formats. The renderer presently copies compatible submitted textures directly into compositor eye slices or presents black when no compatible frame exists; it does not synthesize a scene or provide game readiness.

## Current limits and setup

- Source adapters, source overlays and build recipes are included. Wine/FEX/DXMT native archives require real visionOS builds, and OpenComposite/OpenXR DLLs require a Windows toolchain. No binaries are supplied. Initial graphics support is D3D11; Vulkan/D3D12 are not implemented.
- JIT preparation requests the app's Madeira debugger script through the configured StikDebug/StikJIT URL scheme. That helper must be installed and paired; debugger attachment alone does not mean FEX JIT memory is prepared or that execution will succeed.
- The sample manifest is metadata only. Supply a game you are legally entitled to use and select its containing folder in the app.
- The XcodeGen project consumes the sibling Swift packages at `../windows-vr` and `../windows-vr-metal` and targets visionOS 27.0 for M2-class hardware as the initial research target. Project generation and compilation have not been performed. If future build execution is authorized, install XcodeGen separately if needed, generate the project from this directory, and configure a development signing team in Xcode; the project does not hardcode a paid team.
- No tests, builds, compilation, linters, probes, benchmarks, app launches, or installs were performed for this phase. Source changes and integration remain unverified. Upstream source caches were acquired previously; no native runtime was compiled and no game was imported or executed.
- No privileged entitlements or local-network permission are declared. Add a local-network usage description only if a real feature later needs local networking, with a concrete rationale.

See `Examples/sample-manifest.json` for the version-1 manifest shape. `WindowsGameManifest.validate()` checks the relative executable path, and the bridge verifies that the resolved executable is a regular file contained by the selected folder before dispatch. The app itself does not load the game executable. See `../windows-vr-tools/README.md` for separate source/resource preparation. Never reuse native iOS archives for visionOS; stage Wine resources under `Resources/Runtime` and combined guest outputs under `Resources/WindowsVR/Guest/x64`. Preserve upstream notices and do not distribute game files or credentials.
