# Madeira Windows runtime plugin adapter

`WindowsVRRuntimePlugin.mm` is a project-owned adapter over the real Madeira app bridges. The host must compile it together with the project-owned patch in `patches/0001-Madeira-launch-profile.patch` and the Madeira app-layer `WineProcessBridge.m`, `WineServerBridge.m`, `FEXBridge.mm`, `JITAllocator.c`, and `PrefixExtractor.c`. Apply patches only to a generated source overlay; do not edit the pinned vendor checkout.

The adapter accepts the WindowsVR ABI v1 JSON fields `schemaVersion`, `backend`, `graphics`, `gameDirectory`, `executablePath`, `arguments`, and optional `environment`. It validates the selected PE architecture and executable containment, seeds and validates the Wine prefix, maps the app-bundled guest runtime into that prefix, mounts only the caller-selected game directory, configures Madeira's exact executable/argv bridge, starts wineserver, waits for readiness, and then starts Wine. Both Windows backends require the app's script-capable JIT debugger to remain attached and the kernel to report a live tracer. The plugin calls Madeira's actual JIT fallback; the x64 FEX path additionally initializes FEX and exports its actual JIT pool aliases. Native ARM64 PE requests skip FEX but still use Madeira/Wine and the debugger-mediated JIT preparation.

OpenXR selection is based on the executable's PE machine and app resources, never on the FEX backend choice. AMD64 requires `Bundle.main.resourceURL/WindowsVR/Guest/x64/{wvr_openxr.dll,OpenComposite/bin/vrclient_x64.dll}`. ARM64EC requires the separately built `arm64ec` package at the equivalent path. Other PE machines fail closed until their runtime packages are built. The adapter maps those app-owned resources to `C:\windows-vr-runtime\<abi>` inside the Wine prefix and internally sets `VR_OVERRIDE` to the matching `OpenComposite` directory and `XR_RUNTIME_JSON` to its generated `runtime.json`; callers cannot override either variable. It does not write Wine's system registry or change a host-global active OpenXR runtime. Only Direct3D 11 is accepted; Vulkan is reported unsupported.

A zero return from `windows_vr_launch_v1` means only that the asynchronous request was accepted. Poll `windows_vr_status_v1` and `windows_vr_last_error_v1` for subsequent startup failures. State `running` means Madeira's Wine process bridge is active; it does not claim that the selected game is ready or producing frames. Guest NTSTATUS crashes are surfaced as failed status with an error. A launch attempt consumes the process's single session slot: Madeira's current FEX JIT pool and Wine bridge are not safely restartable in-process.

The upstream Wine bridge detaches its process thread and offers no safe terminate/join API for a live guest. Therefore `windows_vr_stop_v1` returns `EBUSY` while startup or a Wine guest is active; the user must let the guest exit naturally. It reports success after the runtime is already stopped and does not pretend to terminate a live guest. The host must retain the signed framework for the process lifetime.

## Source and framework integration

`WindowsRuntimePlugin.xcodegen.yml` intentionally contains no duplicate target: the authoritative framework target lives in `visionos-windows-vr/project.yml` so it can link the app's exact `WindowsVRMetal` bridge and visionOS-built native dependencies. Rebuild source archives from the generated `runtime-source` overlay; checked-out iOS archives are not compatible inputs. The integration uses FEXCore, Wine Unix libraries, DXMT, cryptography, compression, and database archives from the app target, plus Apple frameworks. It must exclude upstream `wine_stubs.c` and bundled test executables/assets.

The sources call Madeira's existing `wineserver_start`, `wineserver_is_ready`, `wineserver_stop`, `wine_process_start`, `wine_process_is_running`, `wine_exit_status_reset`, `wine_crash_exit_status`, `fex_initialize`, `fex_shutdown`, `fex_get_jit_write_offset`, `jit_arm_trap_fallback`, and `jit_check_debugged` APIs. The project patch adds `wine_process_configure_launch` for exact paths/arguments and `fex_get_jit_pool_info` for the actual RX/RW/size values. These are strong link requirements; there is no weak-symbol or simulated fallback.

This source has not been built or run. Madeira's current FEX bridge allocates a fixed 64 MiB dual-mapped JIT pool and does not expose a pool-release operation, and its Wine bridge cannot safely stop a running guest. The visionOS source retarget, archive compatibility, debugger protocol, Wine startup, and D3D11 output transport still require authorized build and device validation. The project-owned patch `windows-vr-openxr/patches/0001-dxmt-wvr-frame-bridge.patch` adds an Ext2 D3D11 context interface and a WMT Unix dispatch that unwraps actual DXMT textures on the host, inserts producer/consumer shared-event ordering, validates compositor target generation, and submits to the compositor. WMT object handles remain opaque across the guest boundary; the patch deliberately resolves them only inside the host Unix bridge. The OpenXR shim must submit its exact two released projection-view images through Ext2; generic game output-eye identity is not inferred.
